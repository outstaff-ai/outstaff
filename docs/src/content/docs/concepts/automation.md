Outstaff acts without being asked in a few places: it reacts to messages, starts follow-up rounds, hands tickets back and retries stuck work. Each of these has a named switch under `policies` in `.outstaff/team.yaml`. Everything that happens today is on by default; a team that wants less turns a switch off. Anything that merges, approves or acts without a human in the loop is off until a team opts in.

```yaml
policies:
  acknowledge: { chat: true, vcs: true }
  chat: { profile: true }
  design: { canvas: true }
  feedback:
    {
      follow_up_round: true,
      merged_prs: true,
      doc_comments: true,
      ticket_comments: true,
      mentions: true,
    }
  hand_back: { reassign: requester, fallback: first_human }
  tickets: { prs_per_ticket: one, start_moves_active: true }
  pull_ready: true
  merge: { on_approval: false }
  conflicts: { follow_up: true }
  retry: { on_signal: true }
```

Run `ost policies` to see every switch with its effective value and where the value comes from, and `ost workflow explain` to see which switch is behind each rule an event triggers.

## The behaviours

| Switch                                | Default       | What outstaff does while it is on                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------------------------- | ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `policies.acknowledge.chat`           | `true`        | Reacts with eyes to a chat message from a trusted person as soon as the agent has seen it.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `policies.acknowledge.vcs`            | `true`        | Reacts with eyes to each pull request comment the agent is about to answer, when its round starts. Needs a vcs adapter with `vcs.reactions`; `ost validate` warns when it lacks it.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `policies.chat.profile`               | `true`        | Publishes the agent's profile in chat (on Slack, the Home tab): its role, whether it is working or idle with when it was last active, and its current work grouped by ticket or pull request in queue order. Updates when the work changes and at least every 5 minutes while working. Needs a chat adapter with `chat.agentProfile`; `ost validate` warns when it lacks it.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `policies.design.canvas`              | `true`        | Lets a role that declares the `design.canvas` capability (the stock designer) use Claude's Artifact tools to work on a private Design canvas, with an `~/artifacts/` folder that stays across items. Roles without the capability never get them. Needs the `claude-agent-sdk` runtime signed in with a Claude account; `ost doctor` checks the login, `ost validate` warns when the runtime lacks the capability. See [Design canvas](/guides/design-canvas/).                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `policies.feedback.follow_up_round`   | `true`        | Starts another round when feedback arrived after the agent was offered its work, so nothing written during a round is lost.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `policies.feedback.merged_prs`        | `true`        | Schedules the author to answer a trusted person's review or comment on an already merged pull request, and to open a follow-up pull request if a change is asked for.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `policies.feedback.doc_comments`      | `true`        | Schedules the agent who wrote a knowledge document to answer a trusted person's comment or reply on it: it reads the open comments, updates the document, replies to each and resolves a thread only when the last word is its own. The office reads the comments of the documents agents wrote for open work (at most 25 per poll, the most recently active first); the document is linked to its ticket when the agent creates or updates it with `ost doc`. Needs a knowledge adapter with `knowledge.docs`.                                                                                                                                                                                                                                                                                                                                                                                                                |
| `policies.feedback.ticket_comments`   | `true`        | Starts a round for the assigned agent when a trusted person comments on its ticket. On a ticket the agent handed back (assigned to a person, in review or blocked) the comment counts as feedback: the ticket goes back to the agent who last worked on it and moves to active. Comments by agents and by the office never start anything.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `policies.feedback.mentions`          | `true`        | Hands a ticket to the agent a trusted person mentions in a comment on it (`@username`): it is assigned to the agent, moved to active when it is in backlog, ready, review or blocked, and the agent gets a round with the comment. When several agents are mentioned the first takes the ticket and the others get a round to answer on it. A mention in a document comment gives the agent a round on the document, and its ticket goes to the agent when nobody or only a person has it. A mention goes to the agent mentioned, not to the assignee or the last worker. Comments by agents, by the office and by untrusted people never start anything; a done or canceled ticket is left alone.                                                                                                                                                                                                                             |
| `policies.hand_back.reassign`         | `requester`   | When an agent hands work back, moves the ticket to review (done) or to blocked (blocked), and assigns it to the person who asked. A waiting hand-back changes nothing. With `none` the ticket still moves and keeps its assignee.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `policies.hand_back.blocked_notify`   | `pm`          | Who deals with a blocked hand-back before a human is pulled in. With `pm` (the default when the team has a PM role) the office schedules an `unblock` round for the PM with the ticket, the blocked agent and its last comment on the ticket; the PM tries to unblock it (answers, asks a teammate, re-plans) and messages the requester only if a human is needed. With `agent`, or when the team has no PM, the blocked agent tells the requester itself, in its own direct message with the ticket linked, what is needed and where the work is. The thread of a chat item always gets its agent's reply, and items the scheduler blocks are routed the same way. The office never posts to people.                                                                                                                                                                                                                         |
| `policies.hand_back.fallback`         | `first_human` | When a ticket has no known requester, uses the first human in `humans`. With `none`, a rule that needs a requester is skipped when the ticket has none.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `policies.tickets.prs_per_ticket`     | `one`         | Keeps a ticket to one pull request, because the ticket moves to done when its last open pull request merges into the repository's default branch. A merge into another pull request's branch (a stack), or a merge while another pull request of the ticket is still open, leaves the ticket where it is. `ost pr open` refuses a second pull request for a ticket that already has one (open or merged), names it and points to `ost ticket create --parent <ticket>`, which splits the work into sub-tickets, one pull request each. A second pull request a person opens is not refused: the office comments on the ticket that it now has two and that the last to merge closes it. With `many`, several pull requests are allowed and the ticket moves to done only when the agent hands its work back as `done` and every pull request linked to it is closed with at least one merged; a merge alone does not close it. |
| `policies.tickets.start_moves_active` | `true`        | When a work item about a ticket starts, the office moves the ticket to active if it is in backlog, ready or review. A blocked ticket stays blocked until the agent moves it, so a retry that is still blocked ends with the ticket blocked. Work that starts on an open pull request moves a ticket that was closed early back to active. Rounds that only answer something (`asked`, `doc_feedback`) and chat sessions never move it, and neither does the `minimal` preset, which never moves tickets. The agent still keeps the ticket accurate as it goes. A schedule for a ticket that already has a queued or running round of ticket work (`assigned`, `ticket_comment`, `doc_feedback`) joins that round with its feedback instead of starting a second one.                                                                                                                                                           |
| `policies.pull_ready`                 | `true`        | When an agent has nothing queued or running (when a ticket is created or assigned to it or moves into ready, after a hand-back, on the scheduler's tick, when it connects), the office starts its next ready ticket: one assigned to it and in the ready status, the highest tracker priority first, then the one that entered ready the longest ago. A ticket in backlog, one assigned to someone else, and one the agent already worked on since it entered ready are never pulled. This is what starts the tickets an agent assigns to itself, such as the pieces of a split. It counts as automatic work: usage above `usage.pause_automatic_at` stops it while humans are still answered, and the loop guard covers each item.                                                                                                                                                                                            |
| `policies.merge.on_approval`          | `false`       | Lets agents turn on the code host's auto-merge on their pull requests: when an agent marks a pull request ready (`ost pr update <n> --ready`, or `ost pr open` without `--draft`), the same verb turns on auto-merge, or adds it to the merge queue where the repository has one. The repository's rules decide when it merges; no agent runs for the merge and the office only sees it merge. Off by default. Needs a vcs adapter with `vcs.merge`; `ost validate` warns when it lacks it. `ost doctor` checks the code host's merge rules of each repository. See [Merging on approval](#merging-on-approval).                                                                                                                                                                                                                                                                                                               |
| `policies.conflicts.follow_up`        | `true`        | When a pull request starts to conflict with its base, for example after another one merged, sends it back to its agent author to rebase, whatever the status of its ticket: a ticket closed early goes back to active, a canceled one is left alone.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `policies.retry.on_signal`            | `true`        | Retries a blocked work item when a trusted human moves its ticket, assigns it, reviews or comments on its pull request, or replies in its chat thread.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |

`policies.retry` also holds the backoff settings (`base_minutes`, `cap_minutes`, `max_failures`) that decide when a failing item is blocked in the first place.

## Chat and batched wakes in the event pipeline

Proposed ([decision 0016](/decisions/0016-event-pipeline/)), with `office.pipeline: live` in `.outstaff/team.yaml`:

- **A chat message wakes the agent it was written to.** A direct message, a mention or a reply in a thread to an agent is an event like a review or a ticket change. The default policy `chat_to_addressed` starts a chat session for the agent, which decides what the message asks for: an answer, new work, or a change to work it already has. `pipeline.policies.chat_to_addressed` turns it off, narrows it or changes its instruction. In shadow mode the chat desk keeps answering, and `ost explain` shows what the pipeline would have done beside it.
- **Wakes that come close together become one run.** Wakes for the same agent and the same pull request, ticket, document or chat conversation within `pipeline.wake.coalesce_seconds` (default 60) of the first are folded into one run that carries all of them: four review comments left within a minute are one `review_feedback` round, three quick messages are one chat session. The run starts when the window closes. `0` turns it off.

See [Chat in the event pipeline](/architecture/office/#chat-in-the-event-pipeline) and [Coalescing](/architecture/office/#coalescing) for the details.

## Switches and workflow rules

Several switches act on preset [workflow](/reference/team-yaml/#workflow) rules: `feedback.merged_prs` removes `merged-feedback-follow-up`, `feedback.doc_comments` removes `doc-feedback-to-author`, `feedback.ticket_comments` removes `ticket-comment-to-assignee` and `ticket-comment-reactivates-ticket`, `feedback.mentions` removes `mention-assigns-agent`, `doc-mention-feedback` and `doc-mention-assigns-ticket`, `conflicts.follow_up` removes `conflict-back-to-author`, `hand_back.reassign: none` drops the assignment from `hand-back-to-requester` and `hand-back-blocked-to-requester`, `hand_back.blocked_notify: agent` drops the PM round from `hand-back-blocked-to-requester`, and `tickets.prs_per_ticket: many` edits `pr-merged-done`, `pr-closed-ready`, `hand-back-to-requester` and `second-pr-comment` so that a ticket is done when the agent has handed it back as done and its pull requests are all closed with one merged (conditions `ticket_prs_all_closed`, `ticket_prs_open`, `ticket_handed_back` and `ticket_prs_several`). `tickets.prs_per_ticket` is also enforced by `ost pr open`, whatever the preset, so it is not shown as off for the `minimal` preset. The others are carried out by the agent or the office and have no rule behind them.

Precedence, strongest first:

1. A rule in `workflow.rules` with the id of a preset rule. It replaces the preset rule (or, with `disabled: true`, removes it) whatever the switch says, so a team can write its own version of a behaviour and keep the switch off or on.
2. The switch in `policies`.
3. The built-in default.

A switch can only do something the workflow preset has. The `minimal` preset has no `conflict-back-to-author` or `hand-back-to-requester`, so `ost policies` shows those switches as `off` with the source `preset`.

## Merging on approval

```yaml
policies:
  merge:
    on_approval: true
    repos: [app] # optional; default every repo an agent can write to
```

Merging is the code host's job. With the switch on, an agent that marks its pull request ready for review (`ost pr update <n> --ready`, or `ost pr open` without `--draft`) also, in the same verb and as itself, turns on the host's auto-merge, or adds the pull request to the merge queue where the repository has one (a pull request the queue does not take yet gets auto-merge, which joins the queue once the rules are met). From then on the repository's rules decide: once its required approvals and checks are met, the host merges it with the repository's own merge method. No agent is woken for the merge, and the office does not merge: it sees `pr.merged` and moves the ticket as usual. If the host cancels auto-merge (new commits, a conflict, failing CI), the conflict and CI policies send the pull request back to its author, who fixes it and marks it ready again to turn auto-merge back on. If the verb cannot turn auto-merge on (the repository does not allow it, for example), the pull request is still ready, the verb says why, and a person merges it.

An approval schedules nothing. A team that wants an agent to merge explicitly can write its own [workflow](/reference/team-yaml/#workflow) rule that schedules a `merge` item; the agent then runs `ost pr merge <n>`, which checks that the pull request is the caller's own, open, not a draft and mergeable, that an allowed approver (`approvers`) approved its current head with no change requested or review pending, and that the required checks passed, then queues or merges it with `method` (else what the repository has). The same switch allows the verb.

Approvers are people by default. `role:<role>` and agent handles are accepted for a reviewer agent later.

### The code host's rules are the gate

What stops an agent's pull request from merging untested or unreviewed is the code host's own rules: the required status checks and required reviews of the default branch's protection and rulesets. Outstaff only reads them; `repos[].checks` is the list of commands an agent runs before it pushes, not a merge gate, so there is nothing to copy into `team.yaml`. For every repository agents may merge (`merge.repos`, else every repository an agent can write to), `ost doctor office` and the office's own doctor runs (at start, daily and on demand) read the default branch's requirements through the vcs adapter and report:

- an **error** when the branch requires no status check and no approving review;
- a **warning** when it requires only one of the two.

The office stores and logs them with its other doctor checks (`ost doctor --via-office office` shows them) and starts anyway. On GitHub the adapter combines classic branch protection and every ruleset that applies to the branch: required checks are added up, the highest required approval count wins, and the branch must be up to date when any rule says so. Rulesets are read with the office App's Metadata permission. The full classic protection needs Administration: read on the office App; without it the adapter still reads the protected branch's required checks, and doctor warns that the review and up-to-date settings were not read.

### Approvals by GitHub Apps

Whether GitHub counts an approval from a GitHub App toward a branch protection rule's required approvals is not settled. The documentation says required approvals come from "people with write or admin permissions"; approvals by the Actions `GITHUB_TOKEN` count unless the organization turns off "Allow GitHub Actions to approve pull requests"; community reports about a dedicated App or a machine user conflict. Test it on a scratch repository before relying on it: require one approval, let the App approve, and read `mergeStateStatus` and `reviewDecision`.

The design holds either way, because the repository's rules are the gate. If an App's approval does not count, an agent reviewer's approval does not satisfy a repository that requires approvals, and an auto-merge waits for a person's; a team that wants agent reviews to count needs a ruleset that requires no approvals and relies on required status checks instead.

## Checks

An unknown key under `policies` is an error. A switch that is on but needs a capability the configured adapter does not declare, for example `acknowledge.vcs` with a vcs adapter without `vcs.reactions`, is a warning (`policies.capability_missing`); set the switch to `false` to silence it.
