title: Kubernetes
description: Run an office and one agent per person on Kubernetes with plain manifests, secrets as files, a network policy and sized resources.
---

The example in [`examples/k8s`](https://github.com/outstaff-ai/outstaff/tree/main/examples/k8s) is a kustomize base for the synthetic acme team. It uses plain manifests and no operator or chart. CI builds it with a pinned kustomize and validates every resource against the Kubernetes schemas with a pinned kubeconform.

## What you get

| Resource                 | Name                                         | Notes                                                                                                              |
| ------------------------ | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Namespace                | `outstaff-acme`                              | Labelled for the `restricted` Pod Security level, which the manifests meet.                                        |
| Deployment, Service, PVC | `outstaff-office`                            | One replica with `Recreate`, so two offices never share a store. The PVC holds SQLite if you use no Postgres.      |
| StatefulSet, PVC         | `outstaff-agent-<handle>`, `<handle>-home`   | One per person, from one template, each with its own 20 GiB home volume (a plain PVC, so the name is predictable). |
| NetworkPolicy            | several                                      | Default deny; DNS and HTTPS out; agents to the office; the office to Postgres.                                     |
| ConfigMap                | `outstaff-team`                              | Generated from your `team.yaml`.                                                                                   |
| Secrets                  | `outstaff-office`, `outstaff-agent-<handle>` | Generated by kustomize from files you add under `secrets/` (see below). Never in git.                              |

Postgres is not included. Bring your own (a managed database, or your platform's Postgres operator) and give the office its URL in a Secret. Without one, the office stores its state in SQLite on its volume, which is fine to try things out.

## Layout

```text
examples/k8s/
  kustomization.yaml        namespace, resources, images, team ConfigMap, secretGenerator
  secrets/                  your secret files (gitignored) and a README listing them
  namespace.yaml
  network-policy.yaml
  office/                   Deployment, Service, PVC
  agent/                    the template of one agent: StatefulSet and home PVC
  people/<handle>/          person label and patches for the names, the person, the Secret and the volume
```

A person is a folder with a `kustomization.yaml` that reuses `agent/` and patches the StatefulSet name, `OUTSTAFF_PERSON`, the name of the person's Secret and volume, and the PVC name. To add or remove a person, copy or delete a folder, edit the list in the top `kustomization.yaml` and add or remove the person's entry in its `secretGenerator`.

## Deploy

1. **Team file.** Copy your team file next to the kustomization: `cp .outstaff/team.yaml examples/k8s/team.yaml`. For acme, copy `examples/acme/.outstaff/team.yaml`. It is gitignored there.
2. **Images.** Set the release in the `images:` list of `kustomization.yaml`. Use a version tag, or a digest for fully reproducible rollouts.
3. **People.** Edit the list of `people/` folders to match your team file.
4. **Namespace.** `kubectl apply -f examples/k8s/namespace.yaml`.
5. **Secrets.** Add the files under `examples/k8s/secrets/` as described below. They become Secrets when you apply.
6. **Apply.** `kubectl apply -k examples/k8s`.
7. **Check.**

```sh
kubectl -n outstaff-acme get pods,pvc                  # office Ready 1/1, one agent pod per person Running, PVCs Bound
kubectl -n outstaff-acme logs deploy/outstaff-office | grep "agent connected"
kubectl -n outstaff-acme logs sts/outstaff-agent-sam   # why an agent does not start
```

## Secrets

kustomize generates the Secrets from files. Put one file per key in a gitignored tree, `examples/k8s/secrets/office/<KEY>` for the team and `examples/k8s/secrets/<handle>/<KEY>` for each person, and `kubectl apply -k` creates them. A file holds the bare value, so multi-line values such as PEM private keys survive intact. [`secrets/README.md`](https://github.com/outstaff-ai/outstaff/tree/main/examples/k8s/secrets) lists every file per person.

The keys are the acme example's (github, itsaplan, slack and claude-agent-sdk); yours depend on your `integrations` and on each person's repository grants. `ost setup office` and `ost setup <handle>` list them, and the `secretGenerator` in `kustomization.yaml` is where you add or drop a file. Each key of a Secret becomes a file in `/run/secrets/outstaff`, which is where the containers look, so **the key names are the file names**.

| Secret                    | Keys                                                                                                                                                                                                                                                         |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `outstaff-office`         | `GH_OFFICE_APP_ID`, `GH_OFFICE_APP_INSTALLATION_ID`, `GH_OFFICE_APP_PRIVATE_KEY`, `GH_OFFICE_APP_SLUG`, `GH_OFFICE_APP_BOT_EMAIL`, `ITSAPLAN_API_KEY`, `SLACK_OFFICE_BOT_TOKEN`, and `OUTSTAFF_AGENT_TOKEN_<HANDLE>` (upper case) for each person            |
| `outstaff-agent-<handle>` | `OUTSTAFF_AGENT_TOKEN` (the office gets the same value as its token for this person), `ANTHROPIC_API_KEY` (or your other sign-in), `SLACK_APP_TOKEN`, `SLACK_BOT_TOKEN`, `ITSAPLAN_API_KEY`, and the GitHub keys the person's repository grants need (below) |
| `outstaff-office-store`   | `url`: the Postgres URL for the office, `postgres://user:password@host:5432/db`. Optional: without it the office uses SQLite on its volume. Not generated; create it with `kubectl create secret generic outstaff-office-store --from-literal=url=...`.      |

The GitHub keys of a person follow their grants, the same way `ost setup <handle>` lists them. A person with any write grant gets their own App (`GH_APP_ID`, `GH_APP_INSTALLATION_ID`, `GH_APP_PRIVATE_KEY`, `GH_APP_SLUG`, `GH_APP_BOT_EMAIL`) and the office App keys (`GH_OFFICE_APP_*`, including `GH_OFFICE_APP_BOT_EMAIL`). A person with read grants only gets the office App keys. A person with no repository grants, such as the designer `leo`, gets no GitHub keys. The `GH_OFFICE_APP_*` files are stored once, under `secrets/office/`, and the generator copies them into each Secret that needs them. The tree has the same layout `ost setup` writes to `.outstaff/secrets/` (one folder per person and one for the office), so you can copy or link those folders into `secrets/`.

Each agent pod mounts only its own Secret, so an agent never sees another person's secrets or the office's other keys. The generated Secrets carry a hash in their name, which the manifests follow, so changing a file rolls the pods that use it. Files are mounted with mode `0440` and group `10001` (`fsGroup`), so only the container user reads them. To keep the files in 1Password or SOPS instead of typing them in, see the [Secrets guide](/guides/secrets/); it ends with the same files.

Kubernetes Secrets are base64 in etcd. Turn on encryption at rest, limit who can `get` secrets in the namespace, or let an external store fill them (see the Secrets guide). The pods do not mount a service account token, so nothing inside the cluster is reachable through the Kubernetes API from an agent.

## Migrating an existing deployment

A StatefulSet's `selector` and `serviceName` are immutable, so `kubectl apply` cannot change them on StatefulSets you already run. If your agents run from other manifests (or from an older version of this example), move them over without losing their volumes or Secrets. The names below are acme's; use your own.

1. **Keep the old objects.** Copy each old StatefulSet aside as `outstaff-agent-sam-legacy`, with `replicas: 0` and a distinct selector label, for example `outstaff.work/legacy: "true"` in both `selector.matchLabels` and the pod template. Create the copies, so nothing selects both an old and a new pod.
2. **Stop the originals and delete them without their pods or volumes.** Scale each to zero first, then `kubectl delete sts outstaff-agent-sam --cascade=orphan`. The PVCs and Secrets stay as they are. Do not touch them.
3. **Adopt the volumes.** The new manifests expect a PVC named `<handle>-home`. A volume created by `volumeClaimTemplates` is called `home-<statefulset name>` (for example `home-outstaff-agent-sam`). A PVC's name cannot change, so either name the new PVC after the old one (patch `claimName` and the PVC name in `people/sam/kustomization.yaml`) or create `sam-home` from a snapshot or a restored volume. Match the storage class and size of the old claim: a bound PVC is not resized by `apply` to a smaller value.
4. **Provide the new Secrets.** The example generates `outstaff-agent-<handle>-<hash>` from your files and never edits an existing Secret, so the old Secrets stay in place for the rollback.
5. **Create the new objects.** `kubectl apply -k examples/k8s` creates the new StatefulSets, PVCs and Secrets. Check that each agent connects (`kubectl -n outstaff-acme logs deploy/outstaff-office | grep "agent connected"`).
6. **Roll back if needed.** Scale the new StatefulSet to zero and the `-legacy` copy back to one. Only one of the two may run for a person at a time, because both would use the same agent token and home volume.
7. **Clean up** when you are sure: delete the `-legacy` copies, then the old PVCs and Secrets you no longer use.

## Hardening that is already in the manifests

- Every container is non-root (uid and gid 10001), with `readOnlyRootFilesystem`, all capabilities dropped, no privilege escalation and the `RuntimeDefault` seccomp profile. Writable places are the volumes: `/home/outstaff` (an agent), `/var/lib/outstaff` (the office) and a size-limited `emptyDir` for `/tmp`.
- `terminationGracePeriodSeconds` is 45 for the office and 60 for an agent. Both stop on `SIGTERM`: the office finishes its running handlers and an agent hands its work item back, so rolling either is safe.
- The office has a startup probe on `/healthz` with a generous window (three minutes), then a liveness probe on `/healthz` and a readiness probe on `/readyz`. The agent has no port, so no probes: it exits when it cannot run and the StatefulSet restarts it.

## Network policy

`network-policy.yaml` denies all traffic in the namespace, then allows:

- DNS to `kube-dns`;
- TCP 443 to the internet but not to private ranges or the cloud metadata address (`169.254.0.0/16`): the code host, tracker, chat service, LLM provider and tool sources;
- agents to the office on 8080, and nothing else into the office;
- the office to Postgres on 5432. The example allows `10.0.0.0/8`; put the address of your database, or delete the policy if you use SQLite.

This needs a CNI that enforces NetworkPolicy. HTTPS to any public address is broader than the allow-list in the [container contract](/reference/container-contract/) (an agent can run shell commands, and sockets do not ask the permission rules). If your CNI supports it, replace the `ipBlock` rule with FQDN rules for the hosts you name: `api.github.com`, `github.com`, your tracker, `slack.com` and its Socket Mode hosts, and `api.anthropic.com` or your cloud provider's model endpoint. Agents also need the hosts of the tool sources on their first start (the tools install into the home volume and later starts reuse them), so allow those temporarily or build an image with the tools in it ([Container images](/guides/images/)).

## Sizing

These are the starting points from the [container contract](/reference/container-contract/), set as requests, with a memory limit and no CPU limit so a build can use idle CPU. Watch the real use for a week, then adjust.

| Pod                         | Requests             | Memory limit  | Storage                                                                              |
| --------------------------- | -------------------- | ------------- | ------------------------------------------------------------------------------------ |
| Office                      | 0.5 CPU, 512 MiB     | 1 GiB         | 5 GiB volume for SQLite; none needed with Postgres                                   |
| Agent                       | 1 CPU, 2 GiB         | 4 GiB         | 20 GiB home volume (`<handle>-home`)                                                 |
| Agent that builds and tests | 2 CPU, 4 GiB or more | 8 GiB or more | Size the volume for the clones and worktrees of every repository the person works in |

Give an agent that runs your tests the memory of your biggest test run, not of the agent. Raise it with a patch in that person's `people/<handle>/kustomization.yaml`, so one person can differ from the rest. Size the home volume for the installed tools, the clones and the worktrees, and cap `ephemeral-storage` so one runaway job cannot fill a node. The first start of an agent installs its tools and takes longer than later ones.

